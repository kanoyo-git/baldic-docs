# Жизненный цикл и владение

Порядок загрузки DLL, выполнение entrypoints и готовность игры — разные события. `Init` пригоден для регистрации возможностей; игровые объекты создаются и уничтожаются вместе со сценами, а контент готовится в loading stages.

| Манифест | Метод | Назначение |
|---|---|---|
| `preLaunch` | `PreLaunch` | Регистрация после запуска плагинов и разрешения графа |
| `init` | `Init` | Основные регистрации |
| `postInit` | `PostInit` | Завершение и взаимодействие с зарегистрированными сервисами |
| `assetsStart` | `AssetsStart` | Начало игрового loading pipeline |
| `assetsPre` | `AssetsPre` | Подготовка контента |
| `assetsPost` | `AssetsPost` | Работа после основной подготовки |
| `assetsFinal` | `AssetsFinal` | Финальная стадия |
| `test` | `Test` | Явно включённые native tests |

Первые три стадии проводит общий host. Asset stages запускаются игровым API; Loader-only установка не обещает вызвать их автоматически. Нативный `preLaunch` уже слишком поздний для изменения формы загруженного типа — для этого есть [ранняя загрузка](early-pipeline.md).

## ModContext

Контекст содержит `Id`, `Version`, `Root`, `Config`, `Phase`, `Active`, `Faulted` и управление ресурсами. У внешнего плагина есть реальный `PluginInfo`; у обычного пакетного мода он может быть `null`.

Во время вызова entrypoint host устанавливает `ModContext.Current`. Это контекст потока, а не вечное глобальное значение. Отложенный callback не должен предполагать, что Current ещё принадлежит вашему моду. Сохраните явный `ModContext` и входите в него там, где это необходимо.

```csharp
using System;
using Baldic;
using Baldic.Events;

[BaldicMod]
public sealed class OwnedEvents
{
    public void Init(ModContext owner)
    {
        using (owner.Enter())
        {
            EventBus.On("example.ping", data =>
                Log.Info(owner.Id, "Получен ping"));
        }
        // Для стороннего event без автоматического владения:
        Action frame = () => { /* короткая работа в Unity thread */ };
        Driver.Frame += frame;
        owner.Own(new Cleanup(() => Driver.Frame -= frame));
    }
}
```

`EventBus.On` захватывает контекст и регистрирует cleanup. Произвольный C#/Unity event такого поведения не приобретает автоматически. `Driver.Frame` — обычный event; исключение одного обработчика не следует считать изолированным от остальных.

## Объекты и disposable ресурсы

`Own(IDisposable)` вызывает освобождение при завершении владельца. `OwnObject(UnityEngine.Object)` регистрирует созданный вами Unity-объект для уничтожения. Один объект не регистрируется повторно в том же контексте. При уничтожении контекст становится неактивным и увеличивает `Generation`; вход в неактивный или faulted контекст запрещён.

Не передавайте `OwnObject` заимствованный vanilla prefab, material или font: Loader уничтожит его как принадлежащий моду. Создайте собственную копию либо явно сохраните и восстановите изменённое состояние vanilla-объекта.

Cleanup выполняется в обратном порядке регистрации. Чтобы сначала снять ссылку с material, а затем уничтожить texture, регистрируйте восстановление привязки после владения texture.

## Ошибки и перезапуск

Ошибка участника помечает мод и освобождает его ресурсы; зависимые пакеты также могут быть исключены. Ошибка runtime-мода, который уже применил структурные изменения, фатальна: форму загруженного типа вернуть обратно нельзя.

Для ошибки owned callback `Runtime.ReportFailure` сразу устанавливает `Faulted`, а host освобождает ресурсы при обработке очереди ошибок в `Frame`. Не рассчитывайте, что cleanup уже завершён внутри упавшего callback; последующие EventBus-вызовы faulted-владельца пропускаются.

Отключение C#-пакета в меню применяется после перезапуска и не выгружает CLR assembly. `Dispose` контекста освобождает зарегистрированные ресурсы, но не делает замену загруженного DLL безопасной. Unity-объекты и API с thread guard вызывайте из Unity owner thread.
