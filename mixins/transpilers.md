# Собственный transpiler и корректный IL

Transpiler получает инструкции метода во время построения патча и возвращает преобразованную последовательность. Его код не запускается заново при каждом вызове игрового метода. При изменении состава патчей движок может перестроить тело и повторно вызвать transpiler. Поэтому преобразование должно работать с переданной последовательностью и проверять ожидаемый шаблон, а не запоминать, что оно «уже выполнялось».

В новых патчах используйте `Baldic.Mixins.CodeInstruction`. Собственный движок адаптирует эти инструкции в общую цепочку; импортировать `HarmonyLib.CodeInstruction` в такой callback не требуется. Для обёртки вызова, константы или результата выражения сначала рассмотрите [operation helpers](operations.md): они уже реализуют проверку количества совпадений и композицию нескольких регистраций.

## Полный пример

Эта самостоятельная единица требует `0Harmony.dll`. Она заменяет единственную загрузку целого `7` на `31`. Проверка точного количества предотвращает молчаливую установку на неожиданное тело. Новый узел занимает место одной старой инструкции и переносит её метки/границы областей исключений.

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Reflection.Emit;
using System.Runtime.CompilerServices;
using Baldic.Mixins;

namespace Book.Transpilers
{
    public static class Source
    {
        [MethodImpl(MethodImplOptions.NoInlining)]
        public static int Read() => 7;
    }

    public static class TranspilerDemo
    {
        private static IEnumerable<CodeInstruction> Transform(
            IEnumerable<CodeInstruction> instructions)
        {
            var code = instructions.ToList();
            var matches = code.Select((instruction, index) => new { instruction, index })
                .Where(item => item.instruction.opcode == OpCodes.Ldc_I4_7)
                .ToArray();
            if (matches.Length != 1)
                throw new InvalidOperationException("Expected exactly one ldc.i4.7");

            int at = matches[0].index;
            var previous = code[at];
            code[at] = new CodeInstruction(OpCodes.Ldc_I4, 31)
                .MoveLabelsFrom(previous)
                .MoveBlocksFrom(previous);
            return code;
        }

        public static void Run()
        {
            using (var patches = new Patcher("book.transpiler"))
            {
                patches.Patch(AccessTools.Method(typeof(Source), nameof(Source.Read)),
                    transpiler: new PatchMethod(typeof(TranspilerDemo), nameof(Transform)));
                if (Source.Read() != 31)
                    throw new InvalidOperationException("Transpiler failed");
            }
            if (Source.Read() != 7)
                throw new InvalidOperationException("Cleanup failed");
        }
    }
}
```

Это специально узкий учебный шаблон. Для реальной игры недостаточно найти любое число `7`: одинаковая константа может относиться к UI, физике или индексу массива. Ищите содержательное окружение — точный вызов/поле и последовательность соседних инструкций, затем проверяйте ожидаемое число совпадений. При несовпадении остановите установку с диагностикой caller и найденного шаблона.

`Calls(method)` проверяет только `call`/`callvirt` и точный operand `MethodInfo`. Публичный `CodeInstruction` не содержит автоматически весь набор matcher/extension-методов стороннего Harmony API. Стройте поиск на реальных членах собственного facade, а не переносите случайный пример с `CodeMatcher` без проверки доступного контракта.

## Стек и операнды

IL — стековая программа. Замена инструкции должна сохранить типы и количество значений, нужных последующему коду. Например, `ldc.i4` кладёт одно значение int32, `call` забирает параметры и receiver для нестатического метода и кладёт результат, если он не `void`. Схожее имя метода ещё не гарантирует одинаковую сигнатуру стека.

Не заменяйте `callvirt` на `call` только ради удобства: это может изменить виртуальную диспетчеризацию и поведение null receiver. Учитывайте prefixed instructions (`constrained.`, `tail.` и другие), generic-контекст, `ref`/`out`, ветвления и все выходы из метода. Обычный успешный проход по одному пути исполнения не доказывает валидность остальных путей.

Входящая последовательность может уже содержать преобразования других владельцев. `Patcher.GetCurrentInstructions(target)` позволяет получить текущие transpiled instructions для исследования. Это не неизменяемый эталон исходной игры и не гарантия, что другой transpiler не изменит цепочку позже.

## Метки переходов

`instruction.labels` содержит метки, определённые в этой позиции. Operand ветвления ссылается на `Label`, а `switch` — на набор меток. Если удалить отмеченную инструкцию без переноса меток, переход потеряет цель. Если скопировать одну метку на два узла, получится повторное определение.

`MoveLabelsFrom(source)` добавляет метки к новому узлу и очищает их у source. В примере перенос безопасен, потому что один узел заменён одним с тем же эффектом стека. При вставке кода **перед** отмеченной инструкцией нужно решить, должны ли переходы выполнять вставленный код: если да, перенесите входные метки на начало вставки; если нет, оставьте их у прежней инструкции. Это решение о потоке управления, а не косметика.

Для новых ветвлений требуется `ILGenerator`, передаваемый движком в transpiler, и созданные им метки. Не создавайте фиктивный `Label` ради прохождения компилятора C#: у метки должна быть корректная принадлежность генерируемому телу и одна определённая позиция.

## Области исключений

`instruction.blocks` хранит границы try/catch/filter/fault/finally, а не произвольные комментарии. Используются `ExceptionBlock` и `ExceptionBlockType`: начало защищённой области, начало обработчика и окончание области. Для catch имеется `catchType`.

`MoveBlocksFrom(source)` переносит границы целиком и очищает источник. Это подходит для точной замены одного узла в предыдущем примере. При расширении одной инструкции в несколько нужно разнести границы по смыслу: вход в область обычно относится к началу замены, её завершение — к соответствующему концу. Слепой перенос всех blocks на первый добавленный узел способен вынести часть нового кода за границу try/finally или преждевременно закрыть регион.

`new CodeInstruction(existing)` копирует opcode, operand и отдельные списки labels/blocks. Объекты описаний `ExceptionBlock` внутри списка при этом не становятся глубокими независимыми копиями. `Clone()` и его overloads копируют opcode/operand **без** labels и blocks. Это намеренно разные операции. После выбора способа копирования решите, какой единственный выходной узел должен владеть каждой меткой и границей.

## Проверка и снятие

Проверяйте установку на конкретной игровой сборке и исполнение всех затронутых ветвей: обычный результат, ранний выход, исключение, нужные generic/value-type варианты. Ошибка генерации тела — не повод ослаблять проверку шаблона или глотать исключение в transpiler. Сначала изучите фактический IL и цепочку других владельцев.

Снятие owner убирает его transpiler из runtime-цепочки; другие владельцы сохраняются, тело перестраивается согласно оставшимся патчам. Это отличается от ранних структурных преобразований: изменение формы типа до загрузки не откатывается обычным `UnpatchSelf`. Граница этих стадий описана в [совместимости](compatibility.md) и [раннем конвейере](../loader/early-pipeline.md).
